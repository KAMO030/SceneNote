# 场记 SceneNote · 面试速通手册

> 给第一次接触这个项目的人：先花 10 分钟把「一句话介绍 + 数据流 + 5 个决策 + 数字卡」背下来，剩下的按需翻。所有数据来自 `docs/验收记录/`，都是真机测出来的，不是编的。

---

## 0. 30 秒电梯介绍（背下来）

> 场记是一个纯客户端的 AI 语音转文字 + 实时翻译 App，用 Kotlin Multiplatform 写的，Android 和 iOS 共用一套核心代码。主打场景是面对面跨语言对话：对方说话，我戴着耳机直接听到译文，手机不用举到对方脸上，也不用外放；顺带能做会议纪要、看外语视频出字幕。识别全部在手机本地跑（sherpa-onnx），翻译可以用自己的云端 Key，也可以完全离线。整个项目没有后端服务器，不内置任何 Key，数据去了哪儿在 App 里有一本账。

三条红线（面试官问「为什么没有 XX」时先想到这三条）：**没有后端；不内置任何 Key；不谈商业模式。**

## 1. 这个项目解决什么问题

| 用户痛点 | 场记的做法 |
|---|---|
| 翻译 App 要掏手机、举到对方面前，对方很膈应；公放译文在公共场合很尴尬 | **输入输出分离**：手机麦克风朝外收对方的声音，译文从我的耳机出来；手机放口袋也能用（M0 仅听） |
| 一台手机既要收音又要出声，互相干扰 | 输入永远是「离说话人最近的内置麦」，输出永远是「听者自己的耳机或面向对方的屏幕」 |
| 会议记了一堆录音没人整理 | 一按即录，端侧转写，停止后 10 分钟内出一份能分享的纪要（没 Key 也有规则版「时间轴要点」） |
| 看外语视频没字幕 | 相册 / 文件 / 直链视频边转边看（S4）；Android 还能抓系统音频给任何 App 加字幕（S1） |
| 担心录音上传 | 识别全在本地；联网只有「用户自己的 Key 调翻译」这一种，四档隐私、逐条记账 |

**场景矩阵**（面试时能说出几个就够）：M0 仅听、M1 耳听·面屏（旗舰）、M3 双屏对话、M4 速译一句、会议卡、S4 文件字幕、S1 系统字幕。设计文档里还有 M5–M12（分耳、双机 P2P、多人同传、网页字幕）和 S2–S8，属于后续版本。

### 2.2 一句话的数据流（面试必讲）

```
麦克风 16kHz PCM（20ms/帧）
  → Silero VAD 切句（预滚 300ms，句尾 hangover 300ms）
  → zipformer 流式识别 → 灰字草稿（partial）
  → 句尾：zipformer 定稿 rev0；VAD 段交给 SenseVoice 重识别得 rev1（只改原文，不改已播的译文）
  → S0 规则清洗（去口癖、去结巴、中英加空格、补标点；原文 rawText 保留）
  → 判向：这句是我说的还是对方说的？（文字脚本 + 声纹 + 两句防抖）
  → 翻译：云端 qwen-mt（1.5s 超时）→ 超时降级端侧 / 显示原文
  → TTS：系统 TTS 或端侧 Matcha，只产 PCM
  → PlaybackQueue → AudioSink → 耳机 / 扬声器
  并行：字幕上屏；对方插话压低音量；会话结束走慢路径 → 对话卡片 / 纪要 → 资料库
```

「**快路径**」= 上面这条实时链，追求 1.5 秒内出声；「**慢路径**」= 会话结束后一次性用 LLM 做纪要 / 润色，追求准。两条路互不阻塞。

### 2.3 状态机（实时会话）

`Idle → Arming（装模型 1–2 s）→ Live（LISTENING / TRANSLATING / SPEAKING / DUCKED）→ Paused（来电 / 打断）→ Ending → Idle`，另有 `NeedForeground`（预热失效）和 `Degraded`。切 M0 ⇄ M1 ⇄ M3 不重启音频，只换判向和输出规则。

## 4. 真实的设计决策（每个都有「当时的选项 + 为什么 + 代价」）

### 决策 1：纯客户端、没有后端、用户自带 Key（BYOK）

- **背景**：这是产品题的硬约束，同时也是隐私卖点——录音不出手机。
- **选项**：a) 自建 BFF 后端代理云 API（第一版设计文档真这么写过）；b) 内置一个「体验 Key」；c) 用户自己填 Key。
- **选了 c**。内置 Key 在 APK 里一定会被反编译出来滥用；自建后端违反约束还要维护。
- **怎么落地**：`core/egress/EgressGate` 是唯一出网口，判定顺序「隐私档 → 逐段授权 → 消费闸门 → 放行并记账」；Key 放 Keychain / Keystore；账本页能看到今天 / 7 天出站了多少字节、估算花了多少钱。
- **代价**：普通用户填 Key 有门槛，所以「零 Key 也能录、能转写、能出规则版纪要」是硬要求，翻译没 Key 时诚实显示「不翻译」而不是偷偷降质量。

### 决策 2：KMP + Compose Multiplatform，而不是 Flutter / RN / 两套原生

- **业务需求**：一个人要双端同步交付；核心难点在音频采集、蓝牙路由、端侧模型这些**必须碰原生 API** 的地方。
- **为什么 KMP**：共享逻辑用 Kotlin，平台层用 expect/actual 直接写 AVAudioEngine / AudioRecord；sherpa-onnx 的 C 库通过 cinterop 嵌进 klib，iOS 上不需要再写一层 Swift 桥。Flutter 走 FFI 也行，但语音管线这种长活协程 + 流的场景 Kotlin 协程 / Flow 更顺手。
- **代价**：Kotlin/Native 的坑不少（正则不支持 `\p{IsHan}`、NSException 要开 `-Xforeign-exception-mode=objc-wrap`、静态 framework 要手动 `-lsqlite3`），iOS 侧 Skia 渲染的兼容问题也踩过一次（见决策 9）。

### 决策 3：端侧识别全押 sherpa-onnx，模型不随包、按需下载

- **选项**：Whisper.cpp（英文强、中文一般、非流式）、系统识别（iOS SFSpeech / Android 依赖 GMS，国内机型不可控）、sherpa-onnx。
- **选 sherpa-onnx** 的理由：同一个运行时能跑流式 zipformer（中英）、SenseVoice（定稿 + 语种判别）、川渝 Paraformer（四川话）、Silero VAD、CAM++ 声纹、Matcha TTS；有 C API；Android 有现成 AAR，iOS 有 xcframework。
- **两阶段识别**：流式模型快但不带标点、英文全大写，所以先出草稿，句尾用 SenseVoice 重识别一遍做定稿（rev1 只覆盖原文，已经播出去的译文不改，避免用户看到「说完的话又变了」）。
- **模型分发**：模型 200 MB 一个，不能全塞进包里。清单里写死 HuggingFace 直链 + hf-mirror 镜像（国内先试镜像）+ 文件大小 + sha256，下载到临时文件校验通过再原子改名。下载也走 EgressGate 记账。
- **代价**：SenseVoice / Paraformer 是 FunASR 许可证（非 Apache），上架前要法务复核——写进了待办而不是假装没看见。

### 决策 4：双速管线——快路径 1.5 秒熔断降级，慢路径 LLM 成稿

- **业务需求**：面对面对话的核心指标是「对方句尾到我耳机出声」的延迟（目标本机口径 P50 ≤ 1.3 s / P95 ≤ 2.0 s，加蓝牙约 1.5 / 2.2 s）；而会议纪要要的是准和结构化，几秒钟没人在乎。
- **快路径**（`FastTranslator`）：云端优先，`withTimeout(1500)`，连续 2 次超时进入 30 秒熔断（期间不再傻等，直接降级），401 这种不可重试错误直接熔断；降级顺序是端侧翻译 → 显示原文 + 原因。翻译时带上一两句上下文（指代一致）和本句命中的术语（≤ 40 条）。
- **慢路径**（`SlowPath`）：有 Key 用 qwen-flash 按 JSON 模板成稿（会议纪要 / 对话卡片），零 Key 用规则版「时间轴要点」；成稿前脱敏（手机 / 邮箱 / 证件号替换，成稿后还原）；**事实守恒**：数字 / 日期 / 金额必须能在原文里找到，找不到就标「有出入」；按风格缓存到 `polish_revisions`，可回滚。
- **为什么不把 LLM 放进快路径**：LLM 首字延迟不稳定，而且本地 LLM 一跑内存就爆（3.6 GB 的手机装不下），所以「本地 LLM 永远只进慢路径」。

### 决策 5：「场景」是产品主语，不做功能堆砌

- **背景**：四版方案（社交传播 / 知识库 / 隐私 / 场景驱动）评审打分，场景驱动 119 分胜出。理由很朴素：只有「场景」能回答用户「几步能开始录」。
- **落地**：每张场景卡打包了语言对、语气、翻译目标、隐私档、识别策略、模式 ID（`ScenePreset`）；首页一按就进；用户可以「复制一张再改」，不合法组合（比如「优先云端」×「不联网」）保存时直接红字拦住（`SceneRules.problem`）。
- **代价**：所有其他功能（分享、术语表、账本）都得变成场景的「参数」而不是并列入口，页面文案也按规范去掉了 M0 / 混合档这类工程词。

### 决策 6：一次真实的「砍需求」——耳机铁律被推翻

- **原设计**：`RouteManager` 有条铁律「输入必须是内置麦 + 输出 A2DP 耳机，不加 HFP / defaultToSpeaker，拔耳机绝不切扬声器」，还有配套验收脚本（拔耳机 100% 不外放、8 小时待机电量、三姿态 × 三噪声矩阵）。
- **决策（2026-09-17）**：「耳机只是一个输出设备，App 不关心」。所有耳机相关铁律和验收项删掉，蓝牙路由交给系统。
- **为什么**：这些验收只有真机 + 一堆耳机型号才能测，一个人根本测不过来，而且它们不影响核心链路能不能跑。先把链路跑通，机型矩阵放到灰度期。
- **面试价值**：这是「范围管理」的真实案例——不是所有写进文档的东西都要做，关卡不过就砍功能、不砍质量。

### 决策 7：判向不用 LID 模型，用「文字脚本 + 声纹 + 两句防抖」

- **问题**：一台手机、一个麦克风，怎么知道这句是我说的还是对方说的？决定翻译方向。
- **选项**：whisper-tiny 做语种识别（要下 98 MB）；只靠声纹；只靠文字。
- **选了组合拳**：中英这种脚本不同的语对，ASR 输出的文字本身就是证据（汉字多就是中文）；声纹 CAM++ 余弦 ≥ 0.6 复核（M4 里我说的话自动注册「我」）；弱证据翻转先沿用旧方向，连续两句同向才翻；用户左右滑气泡翻转，连续纠正 3 次就建议固定方向。
- **代价**：普通话 ↔ 方言这种同脚本语对只能靠声纹；VAD 分不清谁在说，「我一开口就停播」只能在整句判定后触发。

### 决策 8：内存分级装载（数据驱动的决策）

- **数据**：vivo V2054A（3.6 GB）上四个模型全驻留 PSS **899 MB**，只装 zipformer + VAD 是 **351 MB**，再加 SenseVoice 是 701 MB。
- **决策**：`LoadPlan` 只常驻一个流式 + 一个定稿；`MemoryTier` < 4 GB 的机器实时档不带 SenseVoice；端侧 Matcha TTS 在这台机上中文首包 3.2 秒（RTF ≈ 1.1），所以低端机默认系统 TTS。
- **面试价值**：不是拍脑袋，是先跑基准（`bench/asr-bench.jsonl`）再定策略。

### 决策 9：自研设计系统（Apple HIG + Liquid Glass），不用 material3

- **为什么**：产品原型按 iOS 设计（17 张画板），material3 的圆角 / 涟漪 / 字号刻度全对不上，双栈并存又重。于是做了 `core/designsystem`：语义色令牌、Apple 字号刻度、玻璃 Tab 栏 / Dock / Sheet，跟随系统深浅色和无障碍偏好，对比度有单测（4.5:1 / 3:1）。
- **踩坑**：自己用 GraphicsLayer 嵌套画背景模糊，iOS 上 Skiko 在 `RenderNode::drawShadow` 崩（`EXC_BAD_ACCESS`），换成 haze 1.7.3 解决；Android < 12 没有 RenderEffect，走高填充回退。

### 决策 10：SQLDelight + multiplatform-settings，而不是 Room + DataStore

- 统一成一套纯 Kotlin 方案；minSdk 26 的系统 SQLite 是 3.18，不支持 UPSERT，所以 `INSERT OR REPLACE` + 子查询实现；后来发现 `INSERT OR REPLACE` 会触发级联删除把 segments 删掉，改成专门的 `updateAudioPath`——这是 code review 抓出来的。

## 5. 面试常见问答（大白话版）

**Q1：先介绍一下这个项目。**
> 见第 0 节的 30 秒版本。再补一句：现在 Android 和 iOS 都能跑，识别、翻译、出声、会议纪要、视频字幕、术语表、数据账本这些主链路都通了，有 68 个单元测试和 8 份验收记录。

**Q2：为什么用 KMP，不用 Flutter？**
> 这个项目的难点不在 UI，在音频和端侧模型，这些都得贴着原生 API 写。KMP 的 expect/actual 让我在共享层定义「采集 / 播放 / 路由」接口，Android 用 AudioRecord、iOS 用 AVAudioEngine 各自实现，业务逻辑一份。sherpa-onnx 是 C 库，Kotlin/Native 的 cinterop 能直接调，不用再包一层 Swift。协程加 Flow 处理「帧 → 识别事件 → 翻译 → 播放」这种流式管线也很自然。代价是 Kotlin/Native 的坑要自己踩。

**Q3：项目里最难的地方是什么，怎么解决的？**
> 最难的是实时链路的延迟和稳定性。延迟这块我把链路拆成四个打点（VAD 句尾、翻译首字、TTS 首帧、写入声卡），做了个 `LatencyProbe`，自检页直接算 P50 / P95，还能喂 WAV 文件复现，不用每次真人说话。这样每改一处都能量出来。稳定性上最典型的一个 bug：实时会话和视频字幕同时跑的时候直接 SIGSEGV，查下来是两路识别会话共用了一个 native VAD 句柄，改成每个会话独立 VAD、有会话打开时只增量装载不卸载就好了。

**Q4：有没有什么有趣的事？**
> 有个特别「真机」的问题：面对面模式设计了姿态检测——手机竖起来 1.5 秒自动进「面屏」，放平 1 秒回「仅听」。结果我把手机平放桌上打开这个页面，它 1 秒后自动降回仅听了，因为规则没区分「用户主动进的」和「姿态自动进的」。改成只有姿态自动进入的才会自动降级。这种东西模拟器永远测不出来。
> 还有一个：SenseVoice 会把「Today is library」这种英文短句判成日语或韩语，导致定稿变成一堆假名。最后加了个语种白名单，白名单外的定稿丢掉、保留流式草稿。

**Q5：翻译出来为什么会一半中文一半英文？**（自己先说，显得踏实）
> 早期版本有这个现象。原因是流式模型本身是中英混合训练的，听到什么按它判断的语种直接写；再加上 SenseVoice 定稿用 `auto` 判语种，两者判断不一致时同一句会「跳」语言。解决思路是：单语场景把定稿语种固定；原文的语言标签改成按文字脚本判定，而不是写死会话语言；翻译接上以后原文和译文分开显示，用户就不会把识别原文当成译文了。

**Q6：端侧和云端怎么切换？**
> 识别永远在端侧，云端只有翻译和纪要两处，而且只用用户自己的 Key。切换逻辑在 `FastTranslator`：云端 1.5 秒没回来就降级，连续两次超时熔断 30 秒，401 直接熔断；降级到端侧翻译，端侧也没有就诚实显示原文加原因。设计上还有一层 `RoutePolicy × PrivacyMode` 矩阵（自动 / 只本机 / 优先云端 × 四档隐私），场景编辑时不合法的组合保存不了。

**Q7：隐私怎么做的？**
> 三件事：一、所有出网请求必须经过 `EgressGate`，它按「隐私档 → 逐段授权 → 月度消费上限 → 记账」的顺序判；二、Key 只进 Keychain / Keystore，绝不内置；三、有个「数据去向」页面，今天 / 7 天出站了多少字节的文字、录音、局域网，每一条去了哪个域名、估算花了多少钱，数字直接来自账本表，不是估的。模型下载也记账，只是单独列出来。

**Q8：延迟指标是多少，怎么测的？**
> 目标是本机口径句尾到首帧写入 P50 ≤ 1.3 秒、P95 ≤ 2.0 秒，加蓝牙链路大约 1.5 / 2.2 秒。在骁龙 480 的 vivo 上，流式识别 RTF 0.14（比实时快 7 倍），首包 87 ms；喂标准音频、同语恒等翻译时句尾到首音 176–361 ms；系统 TTS 首块 232–395 ms。真实云端翻译的完整 P50 / P95 要用户填 Key 后跑关卡 B 的 20 句脚本，这个我如实说还没跑完整。

**Q9：为什么没有后端 / 账号 / 社区？**
> 是题目约束，也是产品立场：录音是最敏感的数据，不出手机就是最好的隐私方案。多设备协作在设计里是走局域网 P2P（说话方只发音频流，听的人在自己手机上识别翻译），这样多人同传每个人听自己的语言，也不需要服务器。这部分在规格里，还没实现。

**Q10：你是怎么保证质量的？**
> 每个里程碑都有一份验收记录：交付了什么、真机测了什么、数据多少、没做的写清楚。代码有 68 个单元测试，覆盖状态机、判向、熔断、事实守恒这些逻辑。每个里程碑结束前会做一轮对抗式审查（多个视角挑毛病，比如 I1 那轮 49 条发现确认了 26 条修掉）。

**Q11：踩过哪些坑？**（挑两三个讲，别背清单）
> - AndroidManifest 里 `.MainActivity` 按 namespace 解析，跟实际包名不一致，`ClassNotFoundException`，App 在 vivo 上从来没真正启动过——改全限定名。
> - iOS 上先把 AVAudioEngine 当纯输出启动做 TTS 预热，之后 inputNode 的格式变成 0 Hz，录不到音——installTap 前先 stop 引擎。
> - sherpa-onnx TTS 的 Android 回调如果传 Kotlin lambda（indy 生成），JNI 直接崩，必须写成显式的 `Function1` 类。
> - 深链 `scene/listen?autostart=1` 启动过一次后，进程被杀再从桌面打开，系统会原样重放这个 intent，App 自动开始录音——加了个无 UI 的跳板 Activity。
> - 构建层面：AGP 9 的 KMP 插件 DSL 变了、Compose 1.12 要 compileSdk 37、SQLDelight native-driver 静态链接要 `-lsqlite3`。

**Q12：如果再给你时间，下一步做什么？**
> 三件事按优先级：一、端侧翻译（opus-mt 中英语言对包），让零 Key 也能翻；二、双机 P2P（M8），两个人都戴耳机各听各的；三、把关卡 B 的真机数据跑完整，尤其是判向准确率和 30 分钟连续运行的发热。

**Q13：这个项目是你一个人做的吗？分工是什么？**（如实但自信）
> 方案、决策和真机验证是我在推，代码大部分是我和 AI 编程助手一起写的：我定范围、拍板技术选型、在真机上跑验收、记录数据，助手负责按里程碑产出代码和测试。所以我对每个决策为什么这么做、每个数字怎么来的都能讲清楚。

## 8. 可能被追问的深水区（一句话顶住）

- **为什么句尾要等 300 ms（hangover）？** 人说话中间有短停顿，太早切句会把一句话切成两半；300 ms 是矩阵规格里定的，和预滚 300 ms 配合，句首不丢字、句尾不误切。
- **定稿覆盖草稿会不会闪？** 会，所以定稿只改原文；译文如果已经送去 TTS 就不重译，没送的才重译。
- **开放式耳机会把译文录回来怎么办？** 有泄漏过滤：识别结果和最近播过的译文做字符二元组 Dice 相似度，> 0.8 直接丢。
- **对方一直说话怎么办？** M0 里对方连续说是常态，不算插话，不压音量；靠播放队列积压 ≥ 2 句时语速 1.15–1.25× 兜住。
- **发热怎么办？** 四级阶梯：SERIOUS 强制系统 TTS + 字幕降到 5 Hz、关声纹；CRITICAL 暂停 TTS 只出字。
- **为什么不用系统识别？** iOS 的 SFSpeech 语言包不可控，Android 依赖 GMS，国内机型没有；端侧统一用 sherpa-onnx 行为可预期。
- **四川话怎么做的？** 流式草稿仍用中英 zipformer，句尾用川渝微调的 Paraformer 覆盖定稿（非流式），CER 从 14.3 降到 12.2。
